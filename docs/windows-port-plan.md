# 叠绘 / Compositor Windows 版实施方案

修订日期：2026-10-02。第1批只读预览版已经发布，当前推进查看体验增强。第2批编辑和保存仍待兼容性及设备验收后开放。

## 1. 已确定的范围

Windows 10/11 版与 macOS 版位于同一仓库 `Pengjingyu1992/Compositor-ZH`，分别开发、构建和发布。

- Windows 工作集中在新增 `windows/` 目录，以及专属文档和工作流。
- 现有 `Compositor/`、`CompositorTests/`、`CompositorUITests/`、`Compositor.xcodeproj/`、`Config/` 与 macOS 构建脚本维持原状。
- 用户已安装的 macOS 应用、设置、恢复副本和现有发行包维持原状。
- 首期保持 `.comp` v1–11 的现有定义。Windows 持久化锁、任意路径及其他新格式字段列为后续议题。
- Windows 已独立实现并发布；后续批次继续遵守本方案的数据保留和发行隔离纪律。

目标平台先定为 Windows 10 22H2 x64 和 Windows 11 x64。该项是验收目标，实际最低系统与显卡要求需在锁定 Electron 版本并完成实机验证后公布。ARM64 后续安排。

## 2. 技术路线与职责

采用 Electron + Vue 3 + TypeScript，复用 Pentrado 的文档、工具、历史与 WebGL 渲染，构建叠绘的界面和 `.comp` 适配层。

| 模块 | 职责 |
| --- | --- |
| Electron 主进程与 preload | 窗口、菜单、文件选择、受控文件服务、应用设置、系统集成 |
| Vue 界面 | 叠绘布局、工具与属性面板、语言切换、只读/降级说明 |
| 编辑适配层 | 能力判定、共享操作入口、历史标签、异步任务归属与失败处理 |
| Pentrado 引擎 | 文档节点、工具、命令历史、Canvas/WebGL 渲染 |
| `.comp` 兼容层 | 格式验证、保留原数据、字段映射、资源管理及保存 |

Pentrado 的 TypeScript 核心可独立于 Vue 使用，渲染仍依赖 Canvas/WebGL。引擎与界面通过宿主接口获取桌面能力；文件操作经隔离的 IPC 接口提供，渲染页面不直接获得通用 Node.js 或文件系统访问。

依赖锁定到明确版本或提交。优先在适配层实现叠绘的规则；确需改动 Pentrado 时维护可追踪的小补丁、回归样例和原始许可证。来源说明继续感谢 Robbie Tilton / Wonder Assembly LLC 和 Terry Jia / jtydhr88。

## 3. 仓库组织

以下为拟新增结构，不迁移现有 macOS 源码，也不在其 Xcode 同步目录内放入 Windows 文件。

```text

  package-lock.json            # 锁定依赖，实施时选定单一包管理器
  apps/desktop/
    main/                      # Electron 主进程
    preload/                   # 受控桌面接口
    renderer/                  # Vue 界面
  packages/
    editor-adapter/            # 操作许可、任务归属、Pentrado 接入
    comp-bridge/               # 格式、保留数据与资源、保存
    platform/                  # 宿主接口类型与平台能力
    locales/                   # Windows 简体中文/英文词条
  tests/
    fixtures/                  # 合成、可公开的兼容样例
    unit/
    integration/
    e2e/
  scripts/
  AGENTS.md                    # Windows 工作边界与验收约定
.github/workflows/
  windows-verify.yml
  windows-release.yml
docs/

  windows-compatibility.md
```

实施时使用独立 Windows 功能分支，审核后合入同一仓库。公共文档、忽略规则和 CI 触发配置的准备工作单独提交；macOS 应用源码、Xcode 工程、构建命令和发行包维持原状。macOS 既有测试基线与 Windows 验收结果分别汇报。

### 3.1 公共配置准备

- 修订 `docs/project-format.md`：说明 v3 引入混合模式字段，同时列出当前代码接受的 24 种模式；核对调整层种类和其他枚举，文档纠正不改变文件格式。
- `.gitignore` 增补 `node_modules/`、`.vite/`，Windows 的 `out/`、`release/`、`*.asar` 等产物用 Windows 范围规则；避免全仓忽略同名源目录。
- 测试样例提交 manifest 模板、合成素材和生成器；运行时生成 `.comp` 临时目录，保持现有私人项目忽略规则有效。
- 根第三方说明区分 macOS 当前包与 Windows 包。`windows/THIRD_PARTY_NOTICES.md` 随实际打包依赖更新，不提前把计划引入的软件写成已经分发。

300 文件是初次公开快照的历史数量，后续验收依据是允许发布的内容和产物审查，不固定仓库文件数。

### 3.2 CI 路径与标签隔离

- macOS 分支 push 和 PR 可跳过仅涉及 `windows/**`、`docs/windows-*.md`、`.github/workflows/windows-*.yml` 的变更；同时改变 macOS 或公共协议时仍执行相应检查。
- Windows 工作流覆盖 `windows/**`、自身 workflow、Windows 文档，以及影响它的共享格式/许可材料；不能仅设置 `windows/**`。
- GitHub 对 tag push 不执行路径过滤。macOS 与 Windows 必须明确分隔标签触发，例如保留分支触发并分别指定 `v*` 与 `windows-v*`，防止 Windows 发版再触发 macOS 全套测试。
- 路径过滤跳过的必需检查会保持 Pending。当前核查 `main` 的 `protected` 为 false；后续启用必需检查时，采用始终触发的入口与 job 级判断，保持稳定的检查结果。
- 保留手动全量验收入口，并在混合变更和批量导入场景核对触发结果。过滤规则不应成为掩盖新失败的手段。

## 4. `.comp` 兼容与数据保留

### 4.1 文件结构

现有 `.comp` 是包含 `manifest.json` 和 `images/` 的目录包。Windows 首期通过“打开项目”选择该目录。传输时可将目录压缩，使用前解压；单文件封装另列升级方案。

Windows 持久化继续遵守现有 `.comp` 协议，Pentrado JSON 作为内部模型。未知未来版本需要单独判定读取能力，原字段透传不等于获准编辑未来格式。

### 4.2 保留数据层

文档持有不可变的原 manifest、按图层 UUID 索引的原记录，以及原资源引用；编辑节点与这些数据分开存储。保留表在恢复和历史处理中参与状态管理，避免被 Pentrado 的字段白名单序列化丢弃。

保存概念为 `原记录 + 已修改字段路径 + 显式删除字段路径`，而非对象浅合并。

- 顶层、嵌套对象和已知对象中的未知字段均保留。
- 无修改往返保持原版本和字段值；JSON 排版不要求逐字节相同。
- 未改图片和蒙版保留原字节，验证哈希一致；不能仅比较解码后的像素。
- 新增/删除/复制节点必须遵守 UUID 和引用规则。无法正确更新的引用关系使关联操作受限。
- 修改文字/形状像素、重采样、裁剪等操作按现有协议处理派生字段，不保留已失效的可编辑元数据。
- 修改后预览缓存应重建或明确失效，避免继续显示旧 Quick Look 预览。
- 保存前后均做结构和资源验证，Pentrado 新节点不能自动冒充现有 `.comp` 图层类型。

原始资源按内容引用管理并延迟解码，避免每个撤销状态复制整份图片。读取后的保留资源需要稳定缓存，不能在源项目被外部替换后继续按原路径读到另一份内容。

### 4.3 能力与显示分开

分别记录“能否正确渲染”和“能否正确编辑/保存”。只读属性注明原因和来源；不能理解某字段的坐标或引用语义时，限制影响它的操作族，而非仅禁用一个属性控件。

| 情况 | 产品行为 |
| --- | --- |
| 可正确渲染、可安全编辑 | 在通过写入验收后开放对应操作 |
| 可正确渲染、部分属性暂不可编辑 | 只读属性说明与操作限制 |
| 只能使用项目自带预览 | 明示预览来源；不宣称实时渲染或可完整导出 |
| 无可靠预览或项目验证失败 | 给出原因，归入加载/渲染失败统计 |

可编辑/部分编辑/只读比例附样本数、格式版本和图层/效果分布；拒绝加载及渲染失败单列，不隐藏在只读比例中。

## 5. 渲染兼容

Compositor 当前有 24 种混合模式；早期格式说明列出的 9 种并非当前全集。Pentrado 的混合空间、合成空间和 alpha 合成规则分别配置。

`.comp` 适配层建立明确的映射，保持 Pentrado 的全局默认值。sRGB 混合/合成与普通图层 `union` 作为初始候选，逐样例验证。不要仅修改 normal/multiply/darken/lighten 的 `blendSpace` 就声明保真。

验证包括透明背景、半透明像素、组不透明度、通行组、蒙版位置、剪贴关系、图层翻转/旋转/缩放、调整层和效果。RGB 误差与 alpha 误差分别报告；各模式的公式差异与容差单独说明，不用整体平均误差掩盖局部丢层。

当前 Pentrado shader 中 `lab` 与 `perceptual` 走同一 sRGB 转换分支，不宣传为真实 Lab 混合。

黄金图由现有 macOS 版打开公开合成样例并导出，记录版本与来源；无需改动 macOS 代码。基础无抗锯齿样例优先按逐通道差异检查，旋转、文字、效果等样例单列判据。

## 6. 显卡、大图与中文文字

### 6.1 GPU 与内存

当前 Pentrado 需要 WebGL2 和 `EXT_color_buffer_float`。启动时检查能力、纹理/渲染目标限制及实际分配；GPU 上下文丢失后恢复图层资源和预览，并验证 CPU 文档状态保留。

其中间目标使用 RGBA16F，单个 8192×8192 目标约占 512 MiB，多个中间目标加源图和读回副本会迅速增加占用。因此加载、渲染、导出和历史需要共同预算，而非只检查源 PNG 大小。

读回与中间目标分别列账；同尺寸不表示同样的字节数：

| 8192×8192 项目 | 基础容量估计 |
| --- | --- |
| 单个 RGBA16F 中间目标 | 512 MiB；按并存目标数量累加 |
| 当前 RGBA8 `readPixels` 缓冲 | 256 MiB |
| 接收读回数据的 2D Canvas | 约 256 MiB，后端额外占用实测 |
| PNG 编码缓冲、IPC 拷贝、预览和历史 | 各自记录峰值，不能视为免费 |

这些是基础分配估计，实际峰值包含浏览器/GPU 后端开销。导出应限制并发，释放临时资源，必要时分区处理；实现验证前不宣称读回零拷贝。

Pentrado UI 当前存在 4096 的导入内容限制。`.comp` 接入不得静默缩小原图；低分辨率预览必须保留原资源并明示预览尺度。超出可正确处理范围的编辑/全分辨率导出受限。

首轮基准覆盖 1080p、2048 与 4096 方形画布及多图层/蒙版；8192 及大尺寸不规则图作为压力项。记录峰值内存、GPU 分配、预览耗时、导出读回、撤销增长和资源释放，再公布支持上限。暂不承诺软件渲染性能或 macOS 的最大画布规格。

### 6.2 文字

读取时保留文字层原 PNG，避免首次打开即由不同字体引擎重排。文字内容、UTF-16 颜色/字体范围、段落框和字体名称独立校验。

中文 IME 的组合输入/取消/提交、候选框定位、换行、标点、混合字体、多显示器和不同 DPI 均需 Windows 验证。编辑时缺失字体明确提示；未经验证的文字属性保持只读。随包字体仅采用允许再分发的资源并保留许可证，系统字体不复制进发行包。

## 7. 编辑与写入纪律

编辑许可包含：只读模式、目标能力、在途模态操作、具体文档/编辑实例，以及操作影响的引用和派生字段。菜单、按钮、快捷键和宿主接口共用判定。

Pentrado `applyOps` 未提供失败自动回滚。批量操作需预检全部目标，并采用暂存提交或可验证的命令补偿；不能把多个历史命令分组视为事务完成。

异步结果绑定文档身份、编辑实例、基准修订与取消状态；切换项目、关闭窗口或更新修订后，旧结果不得提交。

写入按两级开放：

1. **另存新项目**：在目标同卷暂存目录写入，完成验证后提交，失败不产生被误认为完整的项目。
2. **覆盖保存**：增加磁盘修订指纹、提交日志、保留旧目录和中断恢复；检测外部修改时停止覆盖并提示另存。

Windows 对非空目录的替换涉及多个步骤，不能将两次 rename 称为整体原子保存。覆盖阶段必须模拟各提交步骤的崩溃、文件占用和失败，并验证原项目或可恢复副本仍完整。

临时占用错误采用有限次数的退避，每次重试先核对提交阶段和原目录状态；权限、路径或容量错误直接给出可读原因。重试耗尽后保持旧项目或可恢复备份，并提供另存路径。

覆盖保存阶段增加资源管理器预览、同步客户端和文件扫描占用的验收。OneDrive 等同步目录存在多文件提交与同步相互影响的情况，使用说明建议优先在本地工作目录保存完整项目后再同步副本；同步目录写入支持以实测为准。

恢复副本使用 Windows 独立目录、版本和文档修订信息，不能调用正式保存完成逻辑来清除未保存标记。其开放时间随可安全保存能力推进。

## 8. 应用身份与发行隔离

| 项目 | Windows 方案 |
| --- | --- |
| 显示名 | 叠绘 / Compositor，使用现有图标配色生成 Windows 图标资源 |
| 应用 ID | 已固定为 `org.compositorzh.windows` |
| 配置 | `%APPDATA%/Compositor-Windows/`，当前只保存语言 |
| 缓存与恢复 | Electron 缓存随 Windows 独立 userData；项目恢复副本随编辑/保存批次实现，当前没有恢复写入 |
| 版本 | 独立 Windows 版本，从 `0.1.0-alpha.1` 起；不冒充 macOS 功能等价版本 |
| 标签 | `windows-v0.1.0-alpha.1` 等 Windows 前缀 |
| 初期下载 | 标为预发布，标题注明只读预览版 |
| 产物 | Windows x64 安装 EXE、解压运行 ZIP、对应 SHA-256 |

当前 macOS“检查更新”打开仓库 `/releases/latest`。Windows 更新入口筛选 Windows 标签，初期版本标为 prerelease，避免成为仓库默认 Latest。

Windows 稳定版的发布手册固定以下流程：

1. 发布前记录当前 macOS Latest 的 release ID 和标签；明确预期仍指向哪个 macOS 发行版。
2. 创建草稿、上传并验证附件；创建及最终发布均显式传入 `make_latest: false`。
3. 发布后通过 REST `/releases/latest` 检查实际 release ID/标签，不能只信任 action 输入参数。
4. 若落到 Windows 发行版，恢复预期 macOS 发行版的 Latest 标记并再次查询；校验或恢复失败时发布任务失败，暂停发布完成公告。
5. 同时核对 Windows 更新入口选择到了新的 Windows 包。

GitHub 明确排除 draft/prerelease，并支持 `make_latest`。默认规则不能简化成按 `published_at` 排序；稳定 Windows 版本默认可能占用 Latest。action-gh-release #703 记录过最终发布遗漏该参数的历史问题，现已关闭，不能据此断言当前版本仍有该故障。终态 API 校验作为发布验收保留。

Windows 包不修改 macOS 发行说明或附件。先采用手动更新；安装器签名、自动更新和文件关联独立安排。程序与资源完整随包提供，基本编辑不依赖在线加载远程页面、字体或脚本。

Windows 第三方清单依据锁文件和实际分发包生成，覆盖 Pentrado、vendored Typr、Vue、reka-ui、vue-i18n、ag-psd、Electron 及实际进入产物的传递依赖。Typr 已用于字体解析，不能把许可证保留推迟到文字转曲功能上线。Electron 自身 LICENSE 与 Chromium 的许可文件一起保留，并检查安装包、ZIP 和解包后的文件；随包字体单独列明许可。

macOS 现有 notices 中“不打包完整 Pentrado 编辑器”和“不分发 ag-psd”的描述应明确限定 macOS 包。Windows 声明按实际产物记录，不能把两端统称为同一套依赖。

发布沿用隐私审查与许可证要求：合成测试数据代替私人项目，审查源码、构建路径、图片元数据、日志和包内容，下载公开附件后核对哈希。Windows GUI 软件只能在实际 Windows 系统上确认可用，云端打包成功不等于实机验收。

## 9. 阶段与验收

| 批次 | 交付 | 放行条件 |
| --- | --- | --- |
| 第0批：内部技术验证 | 独立 Electron 原型；GPU/内存/中文输入；基础 `.comp` 加载；内部临时往返保存器 | 基础样例渲染、无编辑守恒、资源引用、GPU 故障及读回可验证；明确可处理范围 |
| 第1批：只读预览版 | 打开真实项目、查看图层和只读属性、缩放、语言切换与兼容覆盖报告 | 打开的项目无写入；正确区分实时画面与自带预览；至少完成真实项目试用；Win10/11 实机查看通过 |
| 第2批：受限编辑版 | 验证通过的操作、撤销重做、另存新项目、对应恢复副本 | 只修改应变字段；引用正确；资源保留；失败不留半成品；Mac→Win→Mac 可核对 |
| 第3批：完整编辑与发行 | 蒙版/剪贴/调整/效果逐项补齐、PSD 导入导出、覆盖保存、安装器与性能优化 | 各功能独立回归；保存中断恢复；PSD 独立读取；Win10/11 安装与真实 GPU 验收 |

第0批的阻断条件是基础显示错误、丢数据、超预算无可控处理方式、GPU 丢失损坏文档、中文输入不可用。高阶属性暂不可编辑可以形成明确范围；不能将加载后静默丢层视为通过。

第1批关闭 `.comp` 编辑和保存入口，包括快捷键及宿主旁路。设置可以正常持久化，项目文件保持只读。内部保存器在临时输出目录验证，提前检验保留数据的设计。

第1批交付兼容覆盖报告：按项目统计可完整编辑、部分编辑、只读与加载/渲染失败，注明样本数、版本、功能组合及分类依据。区分内部已验证的编辑能力与本版实际开放能力；只读预览版不宣称已经开放编辑。真实项目试用和分类在用户本机进行，公开报告只使用匿名汇总，不上传私人项目和路径。

Windows CI 执行类型/单元/集成检查及 Windows Electron GUI 冒烟。普通 Windows 云 runner 无法代替 Windows 10、Windows 11、真实显卡、中文输入法和不同 DPI 的人工验收，报告中逐项标明。

现有 macOS 的 9 个失败用例作为独立基线记录；只将已明确的行为要求转成 Windows 回归，不借此次工作修改 macOS 测试或应用。后续新失败不能用基线解释。
